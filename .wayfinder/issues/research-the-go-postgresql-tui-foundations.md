## Question

Which current, maintained Go packages and platform APIs best support Bubble Tea composition, PostgreSQL access and cancellation, SQL editing, table rendering, clipboard and mouse input, macOS/Linux keychains, configuration, testing, and cross-platform release packaging—and what constraints should later decisions inherit?

## Resolution

Use a CGO-free Go stack, pinned to stable major lines and exact versions in `go.mod`/`go.sum` at bootstrap:

- **Language/runtime:** target Go 1.26.x. It is the current supported release and satisfies pgx v5's Go 1.25+ floor. Keep CI on the current patch and use the `go`/`toolchain` directives rather than depending on whatever Go happens to be installed. [Go release policy and history](https://go.dev/doc/devel/release)
- **TUI:** use `charm.land/bubbletea/v2`, `charm.land/bubbles/v2`, and `charm.land/lipgloss/v2`. Bubble Tea v2 is stable and gives declarative alt-screen, mouse, bracketed-paste, terminal-color, real-cursor, and enhanced-keyboard state through `tea.View`; newer key distinctions need fallbacks because terminal enhancement support varies. Keep one root model as the authority for focus, tabs, modal routing, and layout; child models return messages/commands, and all database/keychain work runs in `tea.Cmd` rather than blocking `Update`. [Bubble Tea v2](https://github.com/charmbracelet/bubbletea/releases/tag/v2.0.0), [Bubbles v2](https://pkg.go.dev/charm.land/bubbles/v2), [Lip Gloss v2](https://pkg.go.dev/charm.land/lipgloss/v2)
- **Editor and grid:** use Bubbles `textarea` for each SQL buffer (Unicode, multiline editing, paste, scrolling) plus `help`, `key`, `spinner`, and `viewport`/`paginator` where useful. Do not add a client SQL parser or syntax-highlighting dependency for v1; PostgreSQL remains the parser. Build the record/result grid as an application model rendered with Lip Gloss, reusing viewport/pagination primitives. Bubbles `table` is a row-oriented `[]string` viewer with vertical selection; it is not enough for cell focus, horizontal virtualization, typed editing, dirty-cell decoration, or staged CRUD. Keep raw/typed PostgreSQL values separate from display strings. [Textarea API](https://pkg.go.dev/charm.land/bubbles/v2/textarea), [Table API](https://pkg.go.dev/charm.land/bubbles/v2/table)
- **Mouse and clipboard:** enable cell-motion mouse reporting and handle click, release, drag, and wheel at the root using explicit layout hitboxes; keyboard bindings must remain complete. Use Bubble Tea v2 `SetClipboard`/`ReadClipboard` (OSC 52) rather than an OS clipboard dependency, preserving CGO-free builds. OSC 52 is not supported by every terminal—copy must report success optimistically, paste must continue to work through bracketed terminal paste, and clipboard-read-only workflows cannot be required. [Bubble Tea clipboard API](https://pkg.go.dev/charm.land/bubbletea/v2#SetClipboard)
- **PostgreSQL:** use native `github.com/jackc/pgx/v5` plus `pgxpool`, not `database/sql`. Create one bounded pool per open connection workspace; `pgx.Conn` is not concurrency-safe and pool construction does not prove connectivity, so explicitly acquire/ping before entering the workspace. Give every connect/query/load/apply command its own cancelable context and request identity so late messages cannot overwrite newer tab state. Cancellation may invalidate/close the underlying connection; treat the pool as the recovery boundary. Always close/collect rows and check terminal row errors. [pgx v5](https://pkg.go.dev/github.com/jackc/pgx/v5), [pgxpool](https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool), [pgconn cancellation](https://pkg.go.dev/github.com/jackc/pgx/v5/pgconn#hdr-Context_Support)
- **SQL safety and support floor:** support PostgreSQL 14+ for v1, matching pgx v5's maintained/tested range. Parameterize values with `$1...`; identifiers cannot be value parameters, so construct schema/table/column names only with `pgx.Identifier.Sanitize`. Discover privilege-visible objects from `information_schema`, supplementing with read-only `pg_catalog` queries for PostgreSQL-specific keys/types. Page queries must have a unique deterministic `ORDER BY`; large `OFFSET` is inherently inefficient, so the browsing decision should prefer keyset pagination when a usable unique key exists. Staged CRUD must apply in an explicit transaction and explicitly commit or roll back—canceling the context used for `Begin` does not auto-rollback a pgx transaction. [pgx support/version policy](https://github.com/jackc/pgx#supported-go-and-postgresql-versions), [PostgreSQL metadata visibility](https://www.postgresql.org/docs/current/infoschema-columns.html), [PostgreSQL LIMIT/OFFSET constraints](https://www.postgresql.org/docs/current/queries-limit.html)
- **Profiles and secrets:** store non-secret, versioned profile JSON under an app subdirectory of `os.UserConfigDir` (`0700` directory, `0600` file, temp-file-plus-rename writes). Use `github.com/zalando/go-keyring` behind a small internal interface; it is actively released, CGO-free, uses `/usr/bin/security` on macOS, and Secret Service over D-Bus on Linux. Store passwords under a stable profile UUID, never host/user labels. Parse connection URLs immediately, remove passwords before persistence/logging, and store the extracted secret separately. Linux desktops must have an unlocked Secret Service collection (normally `login`); headless/minimal environments may not, and the app must offer session-only entry or a clear error—never a plaintext fallback. [Go config directory](https://pkg.go.dev/os#UserConfigDir), [go-keyring platform requirements](https://pkg.go.dev/github.com/zalando/go-keyring)
- **Testing:** use standard `testing` for reducer/state-machine and rendering tests; isolate clock, database, keyring, and clipboard behind interfaces. Use Charm's `github.com/charmbracelet/x/exp/teatest` only as a test dependency for full-program input/output checks because it is experimental and untagged. Use the official Testcontainers for Go PostgreSQL module for integration tests against the oldest and newest supported majors, covering odd identifiers, composite/no primary keys, NULLs, arrays/JSON, privileges, cancellation, concurrency conflicts, and transaction rollback. CI should run `go test ./...`, `go vet ./...`, and `go test -race ./...`; fuzz profile/URL parsing, cell-width/truncation, and identifier/query construction. Keychain unit tests use the internal fake (the package also offers `MockInit`); small OS-specific smoke tests verify real integrations. [teatest](https://pkg.go.dev/github.com/charmbracelet/x/exp/teatest), [Testcontainers PostgreSQL](https://golang.testcontainers.org/modules/postgres/), [Go race detector](https://go.dev/doc/articles/race_detector), [Go fuzzing](https://go.dev/doc/security/fuzz/)
- **Packaging:** use GoReleaser v2 from its official GitHub Action on version tags. Build `darwin/{amd64,arm64}` and `linux/{amd64,arm64}` with `CGO_ENABLED=0`, `-trimpath`, embedded version/commit, per-platform archives, SHA-256 checksums, and release notes. Run `goreleaser release --snapshot --clean` during CI and execute smoke tests on native macOS and Linux runners before publishing; cross-compilation alone does not verify keychain/terminal behavior. Grant only `contents: write` to the release job's `GITHUB_TOKEN`. Apple signing/notarization and artifact provenance belong in the existing release-quality decision; do not silently claim them for an unsigned archive. [GoReleaser builds](https://goreleaser.com/customization/builds/builders/go/), [checksums](https://goreleaser.com/customization/package/checksum/), [GitHub Actions integration](https://www.goreleaser.com/customization/ci/actions/), [GitHub token permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)

No new ticket is required: query execution mode/multiple result sets, mutation identity/conflicts, interaction fallbacks, and signing/notarization already fit the existing SQL, CRUD, prototype, and release-quality tickets.
